## 1. Окно объяснения формулы урона (на доработку)

Сейчас урон считается через 14+ последовательных модификаторов (скилл-множитель,
ammo-множитель, перк-множитель, крит, пробитие щит/корпус, сопротивления цели,
уклонение, kinetic absorb, adaptive resist, splinter resistance, last stand,
reflect/reactive — см. `_fireCannon`/`_fireLaser` в `GameScene.js` и `takeDamage()` в
`Player.js`/`Mob.js`). Игрок не видит разбивку — только итоговое число.

**Идея:** отдельное окно/панель (из Гаража или из боевого лога) с построчной разбивкой
последнего выстрела/попадания: базовый урон → что добавили скиллы/перки → крит →
пробитие → сопротивление цели → итог. Не меняет саму формулу — только прозрачность для
игрока.

**Статус:** не реализовано, ждёт отдельной проработки UI (куда встроить: Гараж? боевой
лог? тултип по выстрелу?).

## 2. Новые боевые фичи (обсудить отдельно, не багфиксы)

Всё ниже — новый контент/механики с нуля, не доработка существующего:

- **Weapon Heat** — шкала перегрева оружия при непрерывной стрельбе, снижает точность
  выше 80%, блокирует стрельбу на 3с при 100%. Чисто визуально-звуковой слой поверх
  существующего `fireCooldown`, баланс не трогает.
- **Ramming / таранный урон** — столкновение с мобом на высокой относительной скорости
  наносит урон обоим сторонам пропорционально скорости.
- **Environmental hazards** — астероидные поля (замедление/урон), туманности
  (видимость/точность), гравитационные колодцы (искажение траектории снарядов).
- **PvP Kill-feed** — лента убийств в углу HUD (`[PlayerA] 💥 [PlayerB]`).
- **Passive-слот кораблей** — 1 пассивный слот на корабль (выбирается в Гараже) поверх
  существующей активной способности: например "Overdrive" (+15% скорострельность,
  -10% точность), "Fortress" (+10% сопротивление, -15% скорость), "Sniper" (+20%
  дальность, +10% крит, -20% скорострельность).
- **Комбо-метка "Weak Spot"** — лазер по открытому корпусу (щит <10%) ставит дебафф
  "+15% урона от следующей плазмы" на 3с.
- **Данж с отключённым авто-прицелом** (диалог 2026-08-13) — особый данж/арена, где
  авто-лок цели и accuracy-ролл (текущая боевая модель, см. ниже) НЕ работают: игрок
  обязан реально наводить курсором, чтобы попасть. Идея родилась из вопроса "можно
  сделать ручное прицеливание?" — для ВСЕЙ игры решено НЕ делать (авто-лок остаётся
  дефолтом), но как разовая механика конкретного данжа — интересный челлендж-режим
  (см. п.7/8 про данж 50+, та же ниша "особые правила боя для одного места").
  Требует того, что уже описано при разборе фичи: (1) новый инпут — вектор
  корабль→курсор, сейчас курсор не читается для боя вообще; (2) отдельный режим
  поворота корабля в `Player.js` (сейчас поворот — либо "на цель" `faceAngle`, либо
  "по курсу движения" `heading`, независимого "прицел мышью" нет); (3) в PvE — если
  данж работает через realtime-комнату (обычно так), сервер сейчас решает попадание
  ТОЛЬКО по дистанции (`pvp_mob_fire_claim`, `server/main.py`) — нужна server-side
  проверка направления/конуса выстрела, иначе "ручное прицеливание" будет чистым
  плацебо (сервер всё равно засчитает попадание). Не начинать без отдельного
  прохода по объёму (см. вопрос ниже в статусе).

**Статус:** записано, не реализовано. Обсудить приоритет и объём каждого пункта отдельно
перед стартом работы.

## 3. Argus Control — перенести спавн/хил/force-ability на сервер

Сейчас `admin.html` → "Argus Control" управляет боссом через `BroadcastChannel`
(`ArgusController.js`) — это чисто локальный межвкладочный канал ОДНОГО браузера, не
сетевой. Сама логика спавна/фаз/self-heal/force-ability живёт в клиентском коде
(`ArgusController.js`), и `admin.html` может её только попросить исполниться в уже
открытой вкладке с игрой ("живая марионетка" в том же браузере, залогиненная в нужный
сектор) — без неё команда никуда не уходит ("Игра не подключена. Запустите игру в
соседней вкладке браузера."). После спавна урон/абилки уже нормально идут через сервер
(`pvpMobId`, как у обычных мобов) — ограничение именно в ТРИГГЕРЕ действия, не в
дальнейшей синхронизации с другими игроками.

**Запрос:** "зачем админ панели окрытая игра? должно работать с сервером напрямую" —
согласны, это архитектурно правильно, но не мелкий фикс.

**Что нужно:** портировать spawn/despawn/heal/force-ability/фазовую и self-heal логику
Аргуса на Python (`ServerMob`, по образцу остальных server-authoritative мобов — см.
[[server_authoritative_mobs_status]]), чтобы `admin.html` дёргала обычный REST-эндпоинт
(`POST /admin/argus/spawn` и т.п.) без необходимости держать открытую вкладку-марионетку.

**Статус:** не реализовано, отложено — "записать в roadmap, не сегодня".

## 5. Кнопка "Выход" (logout) — ЗАПЛАНИРОВАНО, ждёт подтверждения фикса регистрации

Раз мультиаккаунт на одну почту разрешён (см. диалог "разреши несколько аков на 1
почту"), игрокам нужен быстрый способ выйти и зайти под другим аккаунтом, не закрывая
приложение целиком. **Ждёт**: подтверждения, что фикс регистрации в приложении (CSP,
`v1.1.375`) реально работает — начинать делать logout только после этого.

**Точные требования (из диалога):**

1. Новая кнопка на HUD-панели соц-кнопок (`HudScene.js` `_buildHudSocialButtons()`
   `BTN_DEFS`) — САМАЯ ПРАВАЯ, после существующей `set` (⚙ НАСТРОЙКИ), которая сейчас
   крайняя.
2. По клику — 5-секундный отсчёт (countdown UI, по аналогии с существующими
   countdown/warning-оверлеями, напр. `_showJumpDangerWarning` в GameScene.js).
   - Если корабль **сдвинулся** за время отсчёта (сравнить x/y с моментом старта) —
     отменить выход.
   - Если корабль **атакован** (свежий `player.lastDamageAt`, тот же паттерн, что
     `recentlyHit` в Mob.js — окно ~несколько секунд) — отменить выход И написать в
     лог "выход под атакой невозможен".
3. Данж/босс-карта (`SECTORS[key].isDungeon`/боссовые сектора) — выход РАЗРЕШЁН, но
   ПЕРЕД стартом отсчёта показать предупреждение: "при повторном входе вы будете
   перемещены на ближайшую домашнюю базу — продолжить?" (да/нет). Это не техническое
   ограничение, а честное предупреждение — прогресс инстанса всё равно не резюмируется
   после выхода из игры.
4. По истечении отсчёта без отмены — реальный logout: `clearSession()` (см. api.js),
   остановить игровые сцены, перейти на `LoginScene` (страница авторизации).

**Что переиспользовать:** `_resolveStartSector()` в LoginScene.js уже вычисляет
"домашний сектор корпорации" как фолбэк для недопустимых секторов при входе (сейчас
жёстко исключает только `shadow_arena`/`R-1-boss` — при реализации стоит проверить,
нужно ли обобщить это на ЛЮБОЙ `isDungeon`-сектор, раз ЛЮБОЙ данж теперь может быть
местом выхода).

**Статус:** ✅ РЕАЛИЗОВАНО (кнопка выхода на HUD, отсчёт, отмена на движение/атаку,
предупреждение для данжей — всё по спецификации выше).

## 7. Рельсотрон — новое оружие (привязано к будущему данжу 50+)

Третий тип оружия наравне с пушкой/лазером — "линейный" пробивной архетип, обсуждено
2026-08-09. Источник — новый, ещё не спроектированный данж для карт 50+ уровней (тот же
эндгейм-контент, что уже в бэклоге, см. `roadmap_future.md` п.1 "Данжи 50+").

**Получение:** сборка как лазер (крафт-детали), но материалы — дроп из нового данжа.
**Патроны:** отдельный новый тип боеприпасов (не переиспользует `ammo_plasma`).
**Урон:** -15% от базового урона плазма-пушки того же тира.
**Пассивка загрузки:** "все слоты корабля — рельсотроны" → +5% урона (тот же паттерн, что
`allLasers` в `Player.recomputeStats()`).

**Особые механики:**
- **Точность 100%** — не мажет никогда (не участвует в обычном accuracy-ролле).
- **Уклонение цели ×0.5** — НЕ полный игнор (осознанное решение после обсуждения: полный
  bypass уклонения+точности одновременно обесценивал бы весь uклонение-билд — nimble,
  targeting_ai, evasion-борды). Технически: новый `opts.evasionMult` в `takeDamage()`,
  умножает уже посчитанный `totalEvasion` перед броском рандома — нужно и в
  `Player.takeDamage()`, и в `Mob.takeDamage()` (PvE); для PvP (игрок по игроку) — это
  серверная логика, реальный урон там решает сервер, не клиентский `takeDamage()`.
- **Пробитие по линии** — бьёт ВСЕ цели, стоящие на одной прямой в пределах обычной
  дальности автоогня (`weaponRange = 600`, `constants.js:289` — НЕ через всю карту, та же
  дальность, что у пушки/лазера). Каждая следующая цель по линии получает урон ×0.8 от
  предыдущей (падение 20%/цель).
- **Замедление ремонта цели** — попадание рельсы вешает дебафф на ремонт цели: -5% скорости
  ремонта ЗА КАЖДУЮ рельсу, установленную у стрелка (масштабируется от количества слотов
  стрелка, не цели). Пример из диалога: 7 рельс на корабле → -35% скорости ремонта цели.
  **Действует и на PvP (игроки), и на PvE (мобы/боссы)** — не только PvP, диалог явно
  уточнил это отдельно. Технически два разных места (разные классы):
  - Player.js — `hullRepairPctPerSec`/`cfg.hullRepairDelay`, дебафф по аналогии с уже
    существующими `dotTimer`/`empTimer`/`gravTimer`, новый `repairSlowTimer`/`repairSlowMult`.
  - Mob.js — свой отдельный реген (`shieldRegenDelay`/`shieldRegenFullSec`, см. update()
    ~строка 379) — та же дебафф-механика нужна и здесь, ЭТО НЕ ОБЩИЙ КОД с Player.js (разные
    классы, разные поля регена).
  - Для PvP-целей (другой игрок) — реальный урон/реген решает сервер, значит и этот
    дебафф на PvP-цель тоже должен быть серверным, не только клиентским.
  Открытый вопрос: слот-каунт стрелка или что-то капать — 7×5%=35% само по себе не выглядит
  имбовым (в отличие от истории с Hardened), но стоит перепроверить при реализации не
  складывается ли с чем-то ещё похожим.
  **Длительность таймера: 3 минуты, сбрасывается при прыжке на другую карту** (`galaxy.current`
  меняется — то же самое правило и у аналогичного дебаффа электро-пушки ниже, см. п.8).
- **+5% урона по боссам** — бонус применяется к урону САМОЙ рельсы (не общий), фиксированный
  +5%, НЕ масштабируется количеством установленных рельс (в отличие от пункта выше про
  ремонт) — активен уже при 1 установленной рельсе. Условие — `target.isBoss` (см. `Mob.js`
  `isBoss`/`isDungeonBoss` флаги).

**Технически:** НЕ расширение `Projectile` (тот всегда бьёт ровно одну `victim`) — ближе к
hitscan-лучу лазера (`_laserBeam`), но вместо одного попадания — запрос всех целей вдоль
линии в пределах `weaponRange`, отсортированных по дистанции, с каскадным ×0.8 на каждую
следующую.

**Потолок пробития: 7 целей** (решено 2026-08-09, после того как выяснилось, что изначально
потолка не было вообще — в коридорном данже типа R-1-boss мобы, выстроенные в ряд, могли
дать неограниченное число целей).

**Перки (3, решено 2026-08-09):**
- **Rail Focus** — снижает падение урона по пробитой линии. Пул суммируется по всем рельсам
  (как `perk_steady_aim`): база -3% к падению (20%→17%), макс. прокачка ×1.45 → ~-4.35%.
  **Суб-кап**: падение не ниже ~12% за цель.
- **Neural Jammer** — усиливает игнор уклонения: множитель ×0.5 снижается дальше, база -0.05
  к множителю (×0.5→×0.45), макс. прокачка → ~×0.42. **Суб-кап**: не ниже ×0.30 — иначе
  смыкается с полным игнором уклонения, которого сознательно избегали при исходном дизайне.
- **Boss Hunter** — усиливает бонус урона по боссам. База +3% (поверх базовых +5%, т.е. 8%
  суммарно на 1 копии), суммируется по всем рельсам с этим перком, макс. прокачка ×1.45 →
  +4.35% (итого ~9.35%). **Суб-кап**: суммарный бонус по боссам не выше ~15%.

Все три — тот же принцип, что уже применён к Hardened/Conductive Coils/Arc Extender: пул
суммируется по предметам, но у каждого есть явный суб-кап на итоговый эффект, а не только
надежда, что "никто столько не накопит".

**Статус:** не реализовано, заблокировано отсутствием данжа-источника — концепция
зафиксирована, ждёт создания нового 50+ данжа.

## 8. Электро-пушка — четвёртое оружие (тоже сборка, тоже привязано к данжу 50+)

Обсуждено 2026-08-09, сразу после рельсотрона. **Получение — та же сборка**, что у лазера и
рельсотрона (крафт-детали из нового данжа). **Патроны:** свой отдельный новый тип
боеприпасов (не `ammo_plasma`, не тот же тип, что у рельсы — три разных типа патронов на три
разных оружия физического урона). Пассивка загрузки — как у рельсы: +5% при полном комплекте
этого оружия (тот же паттерн `allLasers`).

**Урон — НЕ идентичен рельсе (пересмотрено 2026-08-09, ради баланса между двумя пушками):**
-20% от плазмы (у рельсы -15%) — этот дополнительный минус компенсируется бонусами ниже.

**Против щита / против голого корпуса — асимметрия, это и есть основная фишка оружия:**
- **+10% урона, ПОКА у цели есть щит** (`weaponShieldMult`-подобный бонус, аналогично тому,
  как у лазера уже есть асимметрия щит/корпус ×0.90/×1.30 в Player.js) — эффективно
  -20%×1.10 ≈ -12% от плазмы против щита, то есть почти не уступает рельсе, пока щит жив.
- **Замедление реген-СКОРОСТИ щита цели: -7% ЗА КАЖДУЮ электро-пушку, установленную у
  стрелка** (7 пушек → -49%). Явно уточнено: это именно скорость подъёма щита
  (`shieldRegenPerSec`), НЕ задержка перед стартом реген (`shieldRegenDelaySec`/кулдаун) —
  разные поля в Player.js, не путать. **Действует и в PvP, и в PvE**, тот же принцип, что и
  дебафф ремонта у рельсы. Технически — длящийся дебафф-таймер (как `dotTimer`/`empTimer`),
  а не мгновенная проверка "стреляют прямо сейчас": реген щита у игрока и так стартует только
  спустя задержку ПОСЛЕ последнего попадания, так что дебафф должен пережить сам обстрел и
  сработать именно в фазе восстановления после боя.
  **Длительность таймера: 3 минуты, сбрасывается при прыжке на другую карту** (тот же таймер-
  стандарт, что и у дебаффа ремонта рельсы, см. п.7 — единообразие между двумя пушками).
- **При попадании по ГОЛОМУ корпусу (щит цели уже на нуле) — замедляет скорость цели на
  10%.** Отдельное условие от бонуса выше — тут никакого урона-бонуса нет, только слоу.
  Не масштабируется количеством стволов (фиксированные -10%, в отличие от реген-дебаффа выше).
  Тоже и PvP, и PvE. **Длительность (уточнено 2026-08-09): держится, ПОКА идёт урон от
  электро по голому корпусу, + ещё до 10 сек после того, как урон прекратился** — то есть
  каждое новое попадание продлевает окно ещё на 10 сек от момента этого попадания (не
  фиксированный таймер от первого хита), плюс сбрасывается при прыжке на другую карту (тот
  же принцип, что у 3-минутных дебаффов выше). Короче/чувствительнее к боевой ситуации, чем
  реген-дебафф — логично, это "пока горячо, цель медленнее" эффект, а не длящееся наказание
  после боя.

**Особая механика — цепная реакция**, не пробитие по линии, а прыжок по БЛИЖАЙШИМ целям:
- **База (без перков): 2 цели всего** — основная + 1 доп. по цепи (100% → 75%).
- **Максимум с перками: 5 целей всего** (основная + 4 доп. по цепи) — см. Arc Extender ниже.
  Прогрессия урона по цепи при полном каскаде (100%, ×0.75 за прыжок): 100% → 75% → 56.25% →
  42.19% → 31.64%.
- Условие прыжка: следующая цель цепи — в пределах **400px от ПРЕДЫДУЩЕЙ** цели (не от
  стрелка) — т.е. цепь может физически уйти далеко от точки выстрела через плотную толпу.

**Оценка/риск — обновлено после ребаланса 2026-08-09.** Первоначальная версия (одинаковый
урон -15%, у рельсы 4 бонуса против 1 у электро) была явно перекошена в пользу рельсы — см.
разбор в диалоге. После ребаланса (электро теряет больше в базовом уроне, но получает
собственную безусловную нишу — щит-бонус + два вида слоу, не зависящие от срабатывания цепи)
асимметрия сгладилась: у обеих пушек теперь по одному безусловному эффекту + одному условному
множественному урону + одному дебаффу, масштабируемому количеством стволов. Открытый вопрос
"радиус прыжка 400px триггерится слишком легко в групповом бою" **всё ещё не решён** — просто
теперь это не единственная проблема баланса пушки, а один из нескольких пунктов, которые
нужно перепроверить вживую при реализации.

**Правило выбора цели для прыжка — НЕ решено, нужно зафиксировать при реализации:**
жадный алгоритм "ближайшая непосечённая цель в радиусе" — самый простой вариант, но не
уточнено (а) есть ли лимит на суммарную дистанцию цепи от исходной точки выстрела, (б) в
PvP-групповых режимах (арена 3v3) — бьёт ли цепь по союзникам стрелка тоже, или только по
врагам.

**Перки (2 новых, спроектированы с учётом урока из истории с Hardened — см. пункт про
рельсотрон/статы):**
- **Conductive Coils** — снижает потерю за прыжок. Пул суммируется по всем электро-пушкам
  (как `perk_steady_aim`): база -3% к потере за прыжок (25%→22%), макс. прокачка ×1.45 →
  ~-4.35%. **Обязательно с суб-капом** на итоговую потерю (не ниже ~15%) — чтобы не повторить
  ситуацию, когда забытый капп на перке даёт нереалистичный максимум (см. историю Hardened).
- **Arc Extender** — +1 доп. цель в цепи за каждую установленную копию. В отличие от
  первоначальной идеи "не суммировать вообще" (по аналогии с фиксом Hardened) — владелец
  явно задал числа: база 2 цели, максимум с перками 5 целей (включая основную). Значит копии
  **суммируются**, но итоговое количество целей **жёстко капается на 5** —
  `Math.min(5, 2 + extenderCount)`. Это тот же принцип защиты от стека, что и у Hardened
  (`hardenedCount < 2`), только капается не число УЧТЁННЫХ копий перка, а прямо конечный
  результат — с фиксированным "+1 цель" (не %) так безопаснее и понятнее, чем считать, сколько
  именно копий пропускать.

**Технически:** тот же класс проблемы, что у рельсотрона — НЕ `Projectile`, а hitscan-луч
`_laserBeam`-типа. Учитывая, что рельса и электро-пушка обе строятся вокруг "1 луч → N целей
с каскадным множителем", имеет смысл делать их вместе и вынести общую часть (резолв списка
целей + применение каскадного урона) в один переиспользуемый хелпер — отличается только
СПОСОБ выбора целей (отсортированные по линии vs жадный ближайший-в-радиусе прыжок) и сам
множитель затухания.

**Статус:** не реализовано, заблокировано отсутствием данжа-источника (тот же, что у
рельсотрона) — концепция зафиксирована, часть решений (радиус прыжка, PvP-friendly-fire,
лимит дистанции цепи) остаются открытыми до реализации.

## 9. Общее ограничение для новых типов оружия: максимум 2 типа одновременно

Решено 2026-08-09, после добавления 3-го и 4-го типа оружия (рельсотрон/электро, п.7-8):
**на корабле одновременно можно держать оружие не более чем ДВУХ типов** из
{плазма-пушка, лазер, рельсотрон, электро-пушка} — не количество стволов, а именно
количество РАЗНЫХ типов среди занятых оружейных слотов.

**Why:** с 4 типами оружия и разными визуальными эффектами выстрела на каждый (болт плазмы,
луч лазера, луч рельсы, дуга электро) — смешать все сразу в одном ряду хардпоинтов
превратится в нечитаемую кашу эффектов на экране. Ограничение прежде всего визуальное/UX,
не боевой баланс.

**Не регрессия для текущей игры** — сейчас в игре ровно 2 типа оружия (плазма+лазер), которые
уже можно свободно микшировать (см. дуальные хардпоинты, реализовано в этой же сессии) —
ограничение становится актуальным только когда появится 3-й/4-й тип, ничего не меняет для
существующих загрузок.

**Технически:** проверка в `GarageScene.equip()` — при экипировке нового оружия в
`gs.equipped.weapon`, посчитать количество РАЗЛИЧНЫХ `item.type` среди уже занятых слотов
(исключая пустые); если тип нового предмета ОТСУТСТВУЕТ среди уже установленных И различных
типов уже 2 — блокировать экипировку с сообщением в лог (тот же UX-паттерн, что уже сделан
для блокировки 3-й копии Hardened).

**Решено:** считать раздельно — 4 отдельных типа (`cannon`/`laser`/`railgun`/`electro`),
БЕЗ укрупнения рельсы+электро в одну "физическую" категорию.
